  步骤 5: 模板渲染

    - destination：plan.destination（字符串字段，非 plan_json 内）
    - days：plan.days（数据库字段，非 plan_json 内）

    - days/budget 来自数据库字段

16. 推荐 Normalized 类型体系
────────────────────────────────────────────────────────────────────────────────

  推荐：方案 A — NormalizedTravelPlan 仅表示规范化后的 plan_json

  理由：
    - 数据库记录（id, title, destination, days 等）不需要 normalize
    - normalizeStructuredTravelPlan 的输入是 plan_json 原始数据
    - 方案 B 把两件事混在一起，职责不清

  类型设计：

  // types/plan.ts

  export interface NormalizedTravelPlan {
    /** 规范化后的结构化计划（plan_json 解析并填充默认值后的结果） */
    plan: StructuredTravelPlan
    /** 规范化过程中产生的非致命警告 */
    warnings: NormalizeWarning[]
    /** 原始 plan_json（调试用，生产环境可通过构建工具移除） */
    _raw: unknown
  }

  export interface NormalizeWarning {
    /** 字段路径，如 "itinerary[0].items[2].resource_type" */
    path: string
    /** 警告代码，如 "UNKNOWN_RESOURCE_TYPE" */
    code: string
    /** 人类可读描述 */
    message: string
    /** 原始值（可选，供调试） */
    rawValue?: unknown
  }

  命名约定：
    - normalizeTravelPlanRecord(plan: TravelPlan): { record: TravelPlan; normalizedPlan: NormalizedTravelPlan | null }
      输入：数据库记录（含 plan_json）
      输出：原始记录 + 规范化后的 plan_json（如 plan_json 为 null 则 normalizedPlan 为 null）

    - normalizeStructuredPlan(raw: unknown): NormalizedTravelPlan | null
      输入：plan_json 的原始值
      输出：规范化结果（含 _warnings, _raw）

  使用方式（detail.vue 替换后）：
    const result = normalizeTravelPlanRecord(plan)
    if (result.normalizedPlan) {
      // 使用 result.normalizedPlan.plan（StructuredTravelPlan）
      // 查看 result.normalizedPlan.warnings
    } else {
      // plan_json 为 null，回退到 markdown
    }


17. Normalizer 函数职责
────────────────────────────────────────────────────────────────────────────────

  函数                                  输入                    输出                    默认值策略
  ──────────────────────────────────────────────────────────────────────────────────────
  normalizeStructuredPlan(raw)          unknown                  NormalizedTravelPlan|null  —（顶层）
  normalizePlanDestination(raw)         unknown                  PlanDestination          缺失字段填默认值
  normalizePlanBudget(raw)              unknown                  PlanBudget               同上
  normalizePlanDay(raw)                 unknown                  PlanDay                  同上
  normalizePlanTimelineItem(raw)        unknown                  PlanTimelineItem         同上
  normalizePlanMeal(raw)                unknown                  PlanMeal                 同上
  normalizePlanHotel(raw)               unknown                  PlanHotel                同上
  validateResourceType(v)               string|undefined         TravelResourceType|'unknown' —
  normalizeCost(v)                      unknown                  number                   非法→0+warning
  normalizeNullableNumber(v)            unknown                  number|null              非法→null+warning
  normalizeStringArray(v)               unknown                  string[]                 非法→[]+warning

  每个子 normalizer 返回标准化对象，副作用是向 warnings[] 追加警告。


18. Normalizer 默认值策略
────────────────────────────────────────────────────────────────────────────────

  场景                          默认值            理由
  ───────────────────────────────────────────────────────────────────────
  plan_json 为 null             返回 null        null = 无结构化数据，页面回退 markdown
  plan_json 为 JSON 字符串      解析后 normalize 先尝试修复
  plan_json 为非法字符串        返回 null+warn  无法恢复
  destination 为字符串          包装为对象       兼容旧数据：{city_id:0,name:dest,province:''}
  budget 为字符串               parseFloat      兼容 DECIMAL 序列化为字符串
  budget 解析失败               0 + warning      不阻塞渲染
  resource_type 缺失/未知       'unknown'+warn   保留原始值在 _raw 中
  resource_id 为 null/undefined null             null 明确表示无 ID（不使用 0）
  resource_id 为非正数          null + warning   同上
  estimated_cost 为负           0 + warning      非法值重置
  estimated_cost 为 null        0                符合后端默认值
  itinerary 缺失                [] + warning     空行程
  days 缺失                     从 itinerary.length 推断+warn  尽力修复
  items 缺失                    []               空活动列表
  meals 缺失                    []               空用餐列表
  hotel 缺失                    null              无住宿

  关键决策：
    1. resource_id 无效时使用 null，不使用 0
       理由：null 明确表示"无关联资源"，0 可能被误认为有效 ID。
       页面在渲染时检查 resource_id !== null 决定是否生成详情链接。
    2. estimated_cost 缺失/非法填 0（符合后端 Schema 默认值）
       UI 通过 fmtCost(0) → "免费" 展示。
       如果 product 需要区分"未知"和"免费"，
       应使用 null → fmtCost(null) → "--"。
       当前 fmtCost 已经处理 undefined/null → "--"。
       建议 normalizer 保留 null 而非转为 0，
       使 UI 能区分"AI 未估算费用"和"免费"。
    3. destination.city_id 缺失时填 0
       理由：兼容旧数据（后端 destination 是字符串）。
       但 city_id:0 不会被误用于 API（前端不拿它查询城市详情）。
    4. 保留 _raw：
       只保留顶层 plan_json 原始值（一个引用），不递归复制。
       开发环境通过 warnings 调试，生产环境 _raw 仍存在但体积可接受。
       （一个 PlanJSON 约 10-50KB，保留一个引用不增加显著内存压力）


19. Normalizer 错误与 Warning 模型
────────────────────────────────────────────────────────────────────────────────

  推荐：方案 A — 直接返回 NormalizedTravelPlan | null，warnings 放在内部

  理由：
    - 大部分字段损坏不阻塞页面渲染（前端可以降级展示）
    - Result 模式增加调用方负担（每次都要 if (!result.ok)）
    - 抛异常过于粗暴（一个字段问题导致整个计划不可见）
    - 当前项目规模不需要 Result 的形式化约束
    - 如果未来需要更严格的错误处理，可以在 NormalizedTravelPlan 中增加 fatalError 字段

  结构化 Warning：
    ✅ 使用 NormalizeWarning { path, code, message, rawValue? }
    不使用自由字符串数组。

    理由：
      - path 方便定位问题字段
      - code 支持程序化处理（如 "UNKNOWN_RESOURCE_TYPE" 可统计）
      - 便于单元测试断言具体 warning


20. schema_version 兼容方案
────────────────────────────────────────────────────────────────────────────────

  推荐方案：

  export type PlanSchemaVersion = '1.0' | '1.1' | (string & {})

  规则：
    1. TypeScript 层面不限制版本号（(string & {}) 允许任意字符串）

28. 风险清单
────────────────────────────────────────────────────────────────────────────────
  R01  plan_json 类型变化导致 api/travel.ts 编译错误
       风险：TravelPlan 类型被 api/travel.ts 多处使用
       缓解：plan_json 改为 StructuredTravelPlan|null 后，
             不访问 plan_json 的函数（getCities/getScenics 等）不受影响。

       风险：硬编码 'scenic_spot' 作为 target_type 值
       缓解：'scenic_spot' 是 SocialTargetType 的子类型，不会报错。

  R03  StructuredTravelPlan 的所有必填字段都给了默认值，
       normalizer 填充后不会出现 undefined 访问。
       缓解：已设计完整默认值策略。

  R04  后端 plan_json 可能不是标准 StructuredTravelPlan
       风险：历史数据、直接 POST 创建的计划可能有不同结构
       缓解：normalizer 处理所有异常情况，降级到 markdown。
