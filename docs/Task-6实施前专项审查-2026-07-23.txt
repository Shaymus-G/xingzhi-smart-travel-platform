3. Transit 后端调用链
────────────────────────────────────────────────────────────────────────────────
  Frontend: GET /api/transit/route?from_type=scenic_spot&from_id=1&to_type=hotel&to_id=2&method=transit&city=杭州
    → transit.py: get_route(from_type, from_id, to_type, to_id, method, city)
    → transit_service.py: get_route()
      → _get_coords(db, from_type, from_id) → (lng, lat) 从数据库查询
      → _get_coords(db, to_type, to_id) → (lng, lat)
      → 根据 method 调用 _call_transit / _call_driving / _call_walking / _call_bicycling
      → 高德 API: https://restapi.amap.com/v3/direction/{mode}
      → 解析响应 → dict
    → response: { code:0, data: {...} }  或  { code:1, message: "error" }


4. /api/transit/route 接口契约
────────────────────────────────────────────────────────────────────────────────
  GET /api/transit/route

  参数         类型    必填  默认      说明
  ─────────────────────────────────────────────────────────────────
  from_type    str     ✅    —         起点资源类型 (5类)
  from_id      int     ✅    —         起点资源 ID
  to_type      str     ✅    —         终点资源类型 (5类)
  to_id        int     ✅    —         终点资源 ID
  method       str     —     "transit" 出行方式
  city         str     —     None      城市名 (公交必填)

  认证: 无需登录
  资源不存在的错误: {"error": "未找到起点/终点资源"}
  缺少坐标: _get_coords 返回 None → error
  高德失败: {"error": "路径规划失败: ..."}
  公交缺city: {"error": "公交模式需要提供 city 参数"}

  关键发现: 前端不需要传经纬度，后端从数据库查询坐标。
  这意味着无需用户当前位置，无需定位权限。

6. 四种交通方式响应差异
────────────────────────────────────────────────────────────────────────────────
  方法        顶层字段                                     独有字段
  ─────────────────────────────────────────────────────────────────────────
  transit     method, distance(米), duration(分钟)          cost(元), walking_distance(米), segments[]
  driving     method, distance(米), duration(分钟)          traffic_lights, toll(元), steps[5]
  walking     method, distance(米), duration(分钟)          steps[5]
  bicycling   method, distance(米), duration(分钟)          steps[5]

  transit segments: { type, name?, departure?, arrival?, via_stops?, distance, duration? }
  其他 steps: { instruction, distance }

  distance/duration 均为字符串 ("12832 米", "45 分钟")，需前端 parse。


7. 当前定位能力
────────────────────────────────────────────────────────────────────────────────
  项目当前: 无任何定位使用
  - uni.getLocation: 0 次调用
  - navigator.geolocation: 0 次
  - Android manifest: 无 ACCESS_FINE_LOCATION / ACCESS_COARSE_LOCATION
  - 微信小程序: 无 scope.userLocation 声明
  - H5: 无 geolocation API 使用

  结论: 项目完全没有定位能力。
  引入定位需要: manifest 权限修改 + H5 HTTPS + 小程序审核 + Android 隐私弹窗。
  且后端 transit API 使用资源 ID 查询坐标，不需要前端传坐标。


8. 是否需要当前位置 — 结论
────────────────────────────────────────────────────────────────────────────────
  由于:
    1. 后端 transit API 接受资源 ID(非坐标)，从数据库查询经纬度
    2. 项目无定位权限配置
    3. 引入定位需要大量跨端 manifest/权限改动

  决策: Task-6 不需要用户当前位置。
  路线查询使用后端已有的资源间路由 (/api/transit/route)。

  这意味着:
    - 详情页无法做"从当前位置到这里"
    - 但计划详情页的相邻资源路线是自然的应用场景


9. 三种实施方案比较
────────────────────────────────────────────────────────────────────────────────
  方案 A: 仅计划详情资源间路线（推荐）
    - 使用 /api/transit/route
    - 不需要定位权限
    - 不需要 manifest 修改
    - 相邻 itinerary item 之间查询
    - transport_to_next 保持不变
    范围: api/transit.ts + TransitRoutePanel + plan/detail.vue

  方案 B: 资源详情间路线 + 定位
    - 需要定位 + manifest 修改
    - 范围大，权限复杂
    范围: 方案A + manifest + scenic/detail + resource/detail + 定位流程

  方案 C: 全功能
    - 需要方案 B 全部 + 计划页 + 城市页
    - 过度设计

  决策: 方案 A
  理由:
    1. 后端 transit API 用资源 ID, 不需要坐标 → 不需要定位
    2. 计划详情已有相邻资源链 (itinerary items), 天然适配
    3. 零 manifest 修改, 零权限问题
    4. 范围最小, 文件最少


10. 计划节点建模
────────────────────────────────────────────────────────────────────────────────
  方案: 只处理相邻 itinerary items

  规则:
    1. 取每个 day.itinerary.items[] 中的连续 item
    2. 当前 item(i) → 下一 item(i+1)
    3. 两端的 resource_type 必须在五类可导航资源中
    4. 两端的 resource_id 必须是正整数
    5. general_activity → 跳过(不作为端点), 也不连接跨越它的两端
    6. unknown → 跳过
    7. 最后一项不显示路线入口 (无下一项)
    8. 不跨天连接
    9. meal/hotel 不参与 (保持简单, 后续可扩展)

  每个可导航段生成:
    { originType, originId, originName, destType, destId, destName }
