7.3 决策理由

  1. 不再需要 SupportedSocialTargetType / PlannedSocialTargetType 阶段性类型。
     原因：后端 _resolve_target 已处理 5 类，交接文档明确声明支持。

  3. RESOURCE_TYPE_META 表消除分散在各页面的 switch/if-else。
     新增资源类型只需在 meta 表中增加一行。

────────────────────────────────────────────────────────────────────────────────

9.1 数据流

  export function normalizePeriod(v: string): string

9.3 适配规则

  输入                        处理                                  输出
  ─────────────────────────────────────────────────────────────────────
  plan_json 为 null          返回 null，页面回退 markdown             null
  plan_json 为字符串          JSON.parse，失败返回 null + warning     object|null
  destination 为字符串        包装为 {name, city_id:0, province:''}   PlanDestination
  destination 为对象          保留，缺失字段填充默认值                 PlanDestination
  budget 为字符串             parseFloat，失败→0                      number
  budget 为数字               原样保留                                 number
  resource_type 未知值        标记'unknown'，保留原名，_warnings追加   string
  resource_id 为 null/0       置为0，保留 name 展示                   number
  estimated_cost 为负         置为0 + warning                         number
  period 中文                 转英文（映射表）                         English period
  itinerary 缺失              默认[]                                  []
  schema_version 缺失         默认"1.0"                                string
  schema_version 未知(>1.1)   标记 warning，继续渲染                   string
  markdown 存在但 plan_json 为 null  使用 markdown 展示               string

9.4 失败策略

  - 不抛异常：部分字段损坏不应阻塞整个页面
  - _warnings 收集所有非致命问题
  - 开发环境：console.warn 输出 warnings
  - 生产环境：静默
  - _raw 保留原始 plan_json 供调试
  - 不使用第三方校验库（zod 等），手写校验逻辑


10. schema_version 决策
────────────────────────────────────────────────────────────────────────────────

10.1 方案比较

  方案   版本   变更内容                                       兼容性
  ─────────────────────────────────────────────────────────────────────
  A      1.0    增加 entertainment/shopping_mall 枚举          兼容
  B      1.1    标记为"扩展资源类型版"，内容同A                 兼容+明确
  C      2.0    同时重构 transport 为对象                      破坏性

10.2 决策：方案 B（升级到 1.1）

  理由：
    1. 资源类型集合从 4 种扩展到 6 种，虽不破坏旧计划解析，但语义上有实质扩展
    2. 版本号变更使消费者（前端、renderer、验证器）能明确区分扩展前后的计划
    3. 历史 1.0 计划继续正常读取（前端适配层兼容未知 resource_type）
    4. 1.1 的结构与 1.0 完全一致，仅 VALID_RESOURCE_TYPES 扩展

  版本路线图：
    v1.0 — 当前：scenic_spot, restaurant, hotel, general_activity
    v1.1 — 本次：增加 entertainment, shopping_mall
    v2.0 — 未来：transport 对象化、weather 结构化 等真正破坏性变更

10.3 实施

  后端 plan_schema.py:
    VALID_RESOURCE_TYPES 增加 entertainment, shopping_mall
    schema_version 默认值改为 "1.1"

  前端适配层:
    识别 1.0 和 1.1 均为兼容版本
    未知版本标记 warning 继续渲染

10.4 不列入 v1.1 的变更

  - transport_to_next 仍为 string | null（不加入实时交通对象）
  - budget.breakdown 不新增 entertainment/shopping 字段（由 AI 自由分配 other）
  - 不改变 PlanJSON 顶层结构


11. 实时交通与持久化边界
────────────────────────────────────────────────────────────────────────────────

11.1 核心原则

  ┌─────────────────────────────────────────────────────────┐
  │ 持久化数据（plan_json）          │  页面运行时状态       │
  ├─────────────────────────────────────────────────────────┤
  │ transport_to_next: string|null   │  TransitRoute 缓存    │
  │ AI 生成的交通建议文本            │  Transit API 实时结果 │
  │ 写入数据库                       │  不写入数据库         │
  │ 通过 PUT 可更新                  │  页面卸载即丢弃       │
  │ schema_version 不受影响          │  不影响 schema_version│
  └─────────────────────────────────────────────────────────┘

11.2 实时交通数据流

  plan/detail.vue:
    1. 默认展示 transport_to_next 文本
    2. 用户点击 "查看路线" 按钮
    3. GET /api/transit/route 请求
    4. normalizeTransitResponse() 规范化
    5. 页面级 Map 缓存 (key: fromType:fromId-toType:toId-method)
    6. 展示 TransitInfo 组件
    7. 失败时保留 transport_to_next 文本，显示 "路线查询失败"
    8. 页面 onUnload 清空缓存 + abort 进行中请求

11.3 transit 类型（types/transit.ts）

  export type TransitMethod = 'transit' | 'driving' | 'walking' | 'bicycling'

  export interface TransitRouteRequest {
    from_type: NavigableResourceType
    from_id: number
    to_type: NavigableResourceType
    to_id: number
    method: TransitMethod
    city?: string  // transit 模式必传
  }

  // 响应类型基于交接文档提供的真实样例
  export interface TransitRouteCommon {
    method: TransitMethod
    distance: string   // "12832 米"
    duration: string   // "45 分钟"
  }

  export interface TransitRouteTransit extends TransitRouteCommon {
    method: 'transit'
    cost: string       // "4.0 元"
    walking_distance: string
    segments: TransitSegment[]
  }

  export interface TransitRouteDriving extends TransitRouteCommon {
    method: 'driving'
    traffic_lights: number
    toll: string       // "0 元"
    steps: TransitStep[]
  }

  export interface TransitRouteWalking extends TransitRouteCommon {
    method: 'walking'
    steps: TransitStep[]
  }

  export interface TransitRouteBicycling extends TransitRouteCommon {
    method: 'bicycling'
    steps: TransitStep[]
  }

  export type TransitRoute =
    | TransitRouteTransit
    | TransitRouteDriving
    | TransitRouteWalking
    | TransitRouteBicycling

  export interface TransitSegment {
    type: string        // "walking"|"subway"|"bus"
    name?: string       // 线路名称
    departure?: string  // 上车站
    arrival?: string    // 下车站
    via_stops?: number  // 经停站数
    instruction?: string
    distance: string
    duration?: string
  }

  export interface TransitStep {
    instruction: string
    distance: string
  }

11.4 关键决策

  - Transit API 主入口使用 /api/transit/route（通用）
  - /api/transit/between-spots 仅作为景点间快捷优化（减少前端传参）
  - general_activity 不允许作为 transit 端点
  - city 参数来源：优先从 PlanJSON destination.name 获取
  - 公交模式 city 必传，非公交模式忽略
  - 前端不持有 AMAP_KEY（密钥在后端 transit_service 中）

13. 城市五类资源架构

13.1 决策

  五类横向滚动 Tab：景点 | 酒店 | 餐厅 | 娱乐 | 商场

14.3 后端非阻塞技术债

  ⚠️ social.py Schema: target_type 仍是 str（无 Pydantic Literal 约束）
     → 前端发送合法类型即可正常工作，但后端应后续收紧
  ⚠️ 无显式目标存在性校验
     → 收藏不存在的 target_id 会成功但回显异常
  ⚠️ 无数据库唯一约束防止重复收藏（当前用 Python 查询防重）

  以上不阻塞前端开发，但必须记录。


15. Transit 架构
────────────────────────────────────────────────────────────────────────────────

15.1 API 封装

  // api/transit.ts

  export function getTransitRoute(params: TransitRouteRequest): Promise<TransitRoute> {
    return http.get('/api/transit/route', filterParams(params))
  }

  export function getTransitBetweenSpots(
    spotAId: number, spotBId: number, method: TransitMethod
  ): Promise<TransitRoute> {
    return http.get('/api/transit/between-spots', { spot_a_id: spotAId, spot_b_id: spotBId, method })
  }

15.2 页面级缓存

  // utils/transit-cache.ts

  class TransitCache {
    private cache = new Map<string, { data: TransitRoute; ts: number }>()
    private TTL = 5 * 60 * 1000  // 5分钟

    key(req: TransitRouteRequest): string {
      return `${req.from_type}:${req.from_id}-${req.to_type}:${req.to_id}-${req.method}`
    }

    get(req: TransitRouteRequest): TransitRoute | null { ... }
    set(req: TransitRouteRequest, data: TransitRoute): void { ... }
    clear(): void { ... }
  }

  每个详情页创建一个 TransitCache 实例，onUnload 时清空。

15.3 计划详情中的交通入口

  每条 PlanTimelineItem 下方：
    - 默认：显示 transport_to_next 文本（"🚗 步行前往下一站"）
    - 按钮："查看路线"（仅当有下一站且两端均有 resource_id 时显示）
    - 点击：展开路线选择器（method 选择 + 实时查询）
    - 结果：在 item 下方展开显示路线详情
    - 失败：保留 transport_to_next 文本 + "路线查询失败，使用AI建议"

15.4 请求取消

  - 详情页 onUnload 时 abort 进行中的 transit 请求
  - 用户切换 method 时 abort 上一个未完成请求

18. 请求和错误策略
────────────────────────────────────────────────────────────────────────────────

18.1 超时配置

  请求类型              超时 (ms)    理由
  ───────────────────────────────────────────────────
  普通 GET              15,000      旅游资源查询
  普通写请求            15,000      登录/注册/收藏/评论
  AI 对话               60,000      DeepSeek 生成
  AI 计划生成           90,000      候选查询+Prompt+DeepSeek+验证+保存
  Transit               15,000      高德地图 API

18.2 请求取消

  - uni.request 返回 RequestTask，存储到页面变量
  - onUnload 时 abort：AI 计划生成、Transit 请求
  - abort 后不显示 toast（用户主动离开）
  - 列表/详情 GET 不取消（响应快，取消无副作用）

18.3 重试策略

  场景                        策略
  ───────────────────────────────────────────────────
  AI 计划生成                  不自动重试（可能已保存，响应丢失会导致重复）
  Transit                      允许手动重试（点击"重试"按钮）
  普通 GET                     不自动重试（用户下拉刷新或点击重试按钮）
  删除操作                     不自动重试（用户确认后手动重试）
  网络错误                     统一提示"网络异常"，不自动重试

18.4 HTTP 错误映射

  状态码    含义                  前端处理
  ─────────────────────────────────────────────────────
  200/201   成功                  正常渲染
  400       参数错误              显示后端 message
  401       未登录                清除 Token → 跳转登录
  404       资源不存在            显示"资源不存在"
  409       重复收藏              显示"已收藏"
  422       校验失败              解析 detail 数组
  500       服务器错误            显示"服务器错误"
  502       AI 格式无效           显示"AI生成失败，请重试"
  503       AI 服务不可用          显示"AI服务繁忙"


19. 状态管理和缓存
────────────────────────────────────────────────────────────────────────────────

19.1 决策：不使用 Plan Store

  理由：
    - 后端已持久化所有计划数据
    - 列表/详情/生成是独立页面导航
    - onShow 重新请求数据比 Store 同步更可靠
    - 删除后通过 onShow 自动刷新

  例外：如果后续需要跨页面"生成中"状态，可以添加轻量 planStore，
        但目前不必要。

19.2 Transit 缓存

  归属：页面局部（每个详情页独立 TransitCache 实例）
  生命周期：页面卸载时清空
  TTL：5 分钟
  不跨页面共享（不同计划的路线没有复用价值）

     缓解：使用渲染后端 HTTPS 地址，或配置局域网 IP
