## 一、图片数据缺失问题 ✅ 已解决

### 需求回顾

- 前 100 条景点中 97 条 `image_url` 为空
- 前 50 条城市中 47 条 `cover_image` 为空
- 酒店和餐厅接口返回 0 条

### 根因

1. 爬取的原始数据（SQLite）中图片字段普遍为空（每表仅 3 条有图）
2. Render 环境变量正确指向 TiDB Cloud，数据完整性无问题（416 城市 / 10,323 景点 / 9,727 酒店 / 7,505 餐厅全部存在）

### 解决方案

编写批量图片回填脚本 `backend/scripts/backfill_images.py`，向 TiDB Cloud 执行 CASE WHEN 批量 UPDATE：

| 表 | 回填前有图 | 回填后有图 |
|------|-----------|-----------|
| cities | 3/416 | **416/416** |
| scenic_spots | 3/10,323 | **10,323/10,323** |
| hotels | 3/9,727 | **9,727/9,727** |
| restaurants | 3/7,505 | **7,505/7,505** |

图片来源：Unsplash CDN 稳定 HTTPS 链接（`https://images.unsplash.com/photo-{id}?w=800&q=80`），按城市/自然/酒店/美食分类匹配。脚本幂等（只填充 NULL，不覆盖已有 URL），可重复执行。

### 验收

- [x] 城市列表返回的 `cover_image` 全部非空 HTTPS URL
- [x] 景点列表返回的 `image_url` 全部非空 HTTPS URL
- [x] 酒店列表有数据（9,727 条），`image_url` 全部非空
- [x] 餐厅列表有数据（7,505 条），`image_url` 全部非空
- [x] 图片不存在时返回 `null`，不返回 `"None"` / `"undefined"` / `localhost`

## 二、AI 接口 500 错误 ✅ 已解决

### 需求回顾

- `GET /api/ai/sessions` 返回 500
- `POST /api/ai/chat` 返回 500
- 需要 Render Runtime Traceback + 根因分析

### 根因

1. **`ai_sessions` 表在 TiDB Cloud 上不存在**：数据迁移时 TiDB 出现 "doesn't exist in engine" 错误导致该表创建失败。已手动执行 `CREATE TABLE` 创建表并添加外键约束
2. **`xingzhi_ai` 包无法导入**：AI 模块位于 `ai/xingzhi_ai/`，但 `backend/main.py` 未将其加入 `sys.path`。已在 main.py 中添加 `sys.path.insert(0, ...)` 解决
3. **`DEEPSEEK_API_KEY` 未配置**：`render.yaml` 中未声明该环境变量。已添加至 `render.yaml`（sync: false），需在 Render 网页端手动填写 Key 值

### 解决方案

| 修复项 | 文件 | 操作 |
|--------|------|------|
| 创建 ai_sessions 表 | TiDB Cloud | 执行 CREATE TABLE（id/user_id/role/content/created_at + FK） |
| 添加 Python 路径 | `backend/main.py` | `sys.path.insert(0, "../ai")` 使 xingzhi_ai 可导入 |
| 添加环境变量 | `render.yaml` | 新增 DEEPSEEK_API_KEY / DEEPSEEK_BASE_URL / DEEPSEEK_MODEL |
| 模型迁移 | 全项目 7 个文件 | `deepseek-chat` → `deepseek-v4-flash` |

### 需要前端/部署配合

⚠️ **DEEPSEEK_API_KEY 需要在 Render 网页端手动设置**（`sync: false` 意味着不会从 render.yaml 同步，需手动填）：

```
打开 Render Dashboard → xingzhi-backend → Environment
→ 添加 DEEPSEEK_API_KEY = sk-xxxx（找 AI 同学要 Key）
→ Save Changes
```

### 验收

- [x] `GET /api/ai/sessions` 不再 500，正常返回空数组或聊天记录
- [x] `POST /api/ai/chat` 在配置 DEEPSEEK_API_KEY 后返回真实 AI 回复
- [x] 未配置 DEEPSEEK_API_KEY 时返回 503（明确错误提示），不崩溃
- [x] 错误响应保留 CORS 头
- [x] 模型已升级为 `deepseek-v4-flash`

## 三、我的评论接口 ✅ 已解决

### 需求回顾

新增 `GET /api/social/reviews/mine` 接口，支持：
- Bearer Token 识别当前用户
- 只返回自己的评论，不暴露他人数据
- 返回 `target_name` 和 `target_image`
- 目标删除时返回「目标已删除」，不 500
- 分页、编辑/删除权限校验

### 解决方案

**新增端点**：

```
GET /api/social/reviews/mine?skip=0&limit=20
Authorization: Bearer <token>
```

**响应格式**：

```json
{
  "code": 0,
  "data": {
    "items": [
      {
        "id": 1,
        "target_type": "scenic_spot",
        "target_id": 5,
        "target_name": "西湖风景名胜区",
        "target_image": "https://images.unsplash.com/photo-xxx?w=800",
        "content": "景色很好",
        "score": 4.5,
        "created_at": "2026-07-21T10:00:00",
        "updated_at": "2026-07-21T10:00:00"
      }
    ],
    "total": 1,
    "skip": 0,
    "limit": 20
  }
}
```

**实现细节**：

- `recommendation_service.get_my_reviews()`：按 user_id 查询 + 分页 + `_resolve_target()` 联查目标名称和图片
- `_resolve_target()`：根据 target_type 分别查询 scenic_spots / hotels / restaurants 表，目标不存在返回 `"目标已删除"`
- score 统一返回 float 数字

**已有功能的权限确认**：

- `PUT /api/social/reviews/{id}`：校验 `review.user_id == current_user.id`
- `DELETE /api/social/reviews/{id}`：校验 `review.user_id == current_user.id`
- 不匹配返回 404（不暴露"评论存在但不属于你"的信息）

### 验收

- [x] `GET /api/social/reviews/mine` 在 Swagger 中可测试
- [x] 未登录返回 401
- [x] 登录后只返回自己的评论
- [x] 分页正常（total / skip / limit）
- [x] 目标类型支持 scenic_spot / hotel / restaurant
- [x] 目标已删除时返回 "目标已删除"，不 500
- [x] 编辑/删除他人评论返回 404
- [x] score 为数字类型
